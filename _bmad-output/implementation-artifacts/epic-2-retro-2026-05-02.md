## Part 1: Epic Review

### What Went Well

**Security foundations were handled as product behavior, not polish.** The epic did not stop at a login page. It covered credential storage, secure cookies, server-side sessions, CSRF, role boundaries, expiry, logout, and structured audit events.

**Review feedback materially improved the implementation.** Several important behaviors were caught and patched during review: malformed hash handling, bootstrap races, open redirect edge cases, proxy trust, stale cookie clearing, expiry redirects, and rolling inactivity cookie behavior.

**The Epic 1 lessons were applied.** `SecretStr`, coverage gating, and robust Alembic root resolution were carried into Story 2.1. The previous retro's most important gates were not left as aspirational notes.

**Tests grew around real risk.** By the end of the epic, auth route, dependency, CSRF, repository, settings, and migration paths all had direct test coverage. The full suite now includes 186 tests.

**Role behavior became explicit.** `require_installer` and `require_homeowner` made access control a dependency-level contract rather than a scattered route convention.

John (Product Manager): "The important product result is simple: users now have distinct local credentials and distinct spaces. That unlocks the rest of the installer and homeowner experience."

Winston (Architect): "The system now has the right security shape. The patterns are plain, testable, and boring in the best way."

### Challenges and Growth Areas

**Security stories generated repeated review patches.** Each auth layer exposed subtle edge cases. That is not a failure, but it shows security checklists need to be even more concrete before implementation begins.

**Story 2.4 carried unresolved CSRF findings into Story 2.5.** Story 2.5 addressed the expiry-related CSRF regression, and the current test suite includes broader CSRF coverage. Remaining CSRF integration concerns should stay visible for future UI stories, especially HTMX header injection in authenticated templates.

**Some behavior changed mid-epic by design.** Story 2.2 initially invalidated existing sessions on login. Story 2.5 intentionally changed the policy to allow multiple sessions. The final behavior is correct, but the transition created extra review and test churn.

**The auth layer depends on future UI work to become fully visible.** Installer and homeowner dashboard routes are placeholders. CSRF token access exists through authenticated users, but real authenticated forms and HTMX fragments arrive later.

Murat (Test Architect): "The suite is healthy, but future UI work must prove the browser actually sends CSRF tokens from rendered authenticated pages. Middleware coverage alone is not the full user path."

### Key Lessons

1. Auth work needs explicit review prompts for redirect safety, proxy trust, cookie clearing, malformed stored data, and concurrent session races.
2. Policy decisions should be settled before implementation stories when possible; the session concurrency shift was handled, but it created rework.
3. Middleware-level security still needs browser-path verification once templates and HTMX interactions exist.
4. Repository and dependency patterns paid off: most fixes were localized and testable.
5. Story records are valuable continuity artifacts. Story 2.5 directly consumed deferred findings from Story 2.4.

### Dependencies From Epic 2

Epic 3 does not directly depend on auth behavior for raw protocol operation. The main dependency is platform maturity: logging, settings, async patterns, test discipline, and migration hygiene.

### Preparation Risks for Epic 3

| Risk | Why It Matters | Action |
|---|---|---|
| Blocking I/O in protocol adapters | The architecture requires protocol adapters not to stall the event loop | Add an adapter implementation checklist covering timeouts and async boundaries |
| External protocol parsing edge cases | Modbus/OCPP/DSMR data can be malformed, partial, stale, or unavailable | Add fixtures for timeout, malformed payload, disconnect, reconnect, and stale data |
| Library selection assumptions | Architecture names likely libraries, but each adapter must stay behind a stable contract | Keep vendor/library types out of domain-facing interfaces |
| Deferred CSRF/HTMX UI integration | Not a blocker for Epic 3, but must be carried into authenticated UI stories | Track as future UI readiness item |

Winston (Architect): "Epic 3 is where we protect the event loop. Auth taught us to make failure behavior explicit; adapters need the same discipline."
