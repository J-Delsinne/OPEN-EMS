## Part 1: What Made Epic 1 Stable

### Successes

**Predictability over speed.** Every story had a clear scope, hard "do NOT create" boundary, and a strict definition of done. No story felt like "we'll figure it out while coding." This removed uncertainty — which is why velocity was high despite never rushing.

**Three-layer feedback loop.** Issues never travelled far:
1. Local: ruff + mypy + pytest caught functional regressions immediately
2. Code review: caught security gaps, edge cases, and environment assumptions
3. CI: caught format violations and integration regressions automatically

Zero regressions across 7 stories is a direct result of this layering.

**Committed to tools early, never revisited.** uv, mypy strict, ruff, structlog, Alembic — decisions made in Story 1.1 and held through Story 1.7 without negotiation. No decision fatigue, no inconsistency to reconcile later.

**Stories were genuinely small.** Story 1.6 was a YAML file. Story 1.1 was a skeleton. Even the heavier stories (1.2, 1.5) had explicit scope limits that prevented them from exploding. Small stories kept cognitive load low and made code reviews effective.

**Accumulated learnings carried forward.** Each story's Dev Notes included a "Previous Story Learnings" section. By Story 1.4, five confirmed gotchas were pre-loaded: `uv` invocation as `python -m uv`, `asyncio_mode = "auto"`, `from __future__ import annotations`, etc. Dev agents didn't repeat the same mistakes.

**Code review found real things every time.** Not nitpicks — real production failures: CWD-dependent `Config("alembic.ini")` (Story 1.2), NTP response not length-validated before `struct.unpack` (Story 1.3), private key file world-readable (Story 1.4). The review layer paid for itself every story.

**Jordan's framing (verbatim):** *"We didn't move fast because we rushed. We moved fast because we removed uncertainty."*

### Honest Assessment of Challenges

**Every story had High-severity findings in review.** No story shipped clean on first pass. This was acceptable in Epic 1 — review was acting as a second layer of design validation while patterns were being established. But it was not free.

**The failure classes were consistent and predictable:**
1. **Security** — file permissions, input validation, credential handling (Stories 1.3, 1.4, 1.7)
2. **Edge cases** — empty values, malformed data, negative numbers (Stories 1.3, 1.5, 1.7)
3. **Environment assumptions** — CWD-relative paths, deployment context, systemd env (Stories 1.2, 1.3, 1.5)

These are predictable categories. The goal for Epic 2+ is to shift detection of these failures from review-stage to dev-stage.

## Part 3: Feedback Loop — Decisions

### Current three-layer feedback loop (retain as-is)

| Stage | Catches | Action |
|---|---|---|
| Pre-commit (NEW) | Format + lint violations | Add `ruff format` + `ruff check --fix` hooks |
| Local dev | Type errors, functional regressions | mypy + pytest (unchanged) |
| Code review | Security gaps, edge cases, env assumptions | Augmented with checklists |
| CI | Full gate | Unchanged |

### Pre-commit hooks — decision

**Add:** `ruff format` (auto-fix) + `ruff check --fix` (auto-fix where possible).  
**Do NOT add:** mypy or pytest — too slow, will get bypassed.  
**Principle:** Hooks fix, they don't block. A commit that triggers the hook leaves a clean diff, not a failed commit.

### Dev-stage checklists — decision

Three targeted checklists to be embedded in story Dev Notes for relevant story types:

1. **File I/O / Security checklist** — for any story touching file writes, credentials, key material, or external secrets
2. **External data / Edge case checklist** — for any story ingesting network data, parsing external formats, or processing user input
3. **Deployment / Environment checklist** — for any story touching paths, environment variables, startup sequence, or systemd/Docker context

**Goal:** Shift predictable High-severity review findings to dev-stage. Not by adding bureaucracy — by making "done well" explicit at the right moment.
