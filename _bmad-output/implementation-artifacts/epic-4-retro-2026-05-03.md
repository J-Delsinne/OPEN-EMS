## Part 1: Epic Review

### What Went Well

**Process discipline held completely.**
Zero open `[ ]` review findings across all five stories at close. This is a direct reversal of the Story 3.3 failure (two unresolved findings that should not have survived review). The structural enforcement introduced in Epic 3's retro — hard closure gates, pre-commit hook checking for open findings — worked as designed. "Functionally complete" ≠ done was not just a rule; it was a mechanically enforced gate.

**Code review functioned as a correctness tool, not a style tool.**
Review consistently caught real implementation bugs before they reached the codebase: `occurred_at` using wall clock instead of `raw.read_at` (Story 4.2), `device_id` inconsistency between success and failure paths (Story 4.2), `_require_reg` accidentally exported as public API (Story 4.2), `_map_telegram` using `raw.device_id` instead of `self.device_id` in violation of the device ID access rule (Story 4.3). These were correctness failures that would have produced incorrect domain state in production.

**Architecture boundaries held under expansion.**
Five stories, two cross-cutting changes, four adapters — the `core/` vs `adapters/` import boundary was never violated. mypy strict mode enforces this mechanically, not by convention. When Story 4.3 required simultaneous changes to `core/devices.py`, `adapters/protocol.py`, and `ocpp/central_system.py`, the boundary constraint remained intact.

**Fake adapter testing pattern scaled to full epic scope.**
The pattern established in Epic 3 scaled to four domain adapters plus `DiscoveryService`. All failure modes — missing registers, `ProtocolDegradedState` translation, staleness checks, OCPP status mapping, DSMR field extraction — tested deterministically without real hardware. 179 new tests covering failure paths, boundary conditions, and lifecycle behavior.

**Scope discipline maintained throughout.**
Five stories delivered exactly the intended scope: normalized device state, capability registry, and discovery signaling. No scope drift, no partial implementations carried forward, no "functionally complete" stories left open.

**All Epic 3 retro action items resolved.**
Seven technical action items (C1–C7), all closed within Epic 4. The structural mechanism — surfacing retro items as explicit story gates — prevented the carry-forward fade that caused A5/A6/A7 to accumulate risk in Epic 3.

### Challenges and Growth Areas

**Story 4.5 had significantly heavier review load than the rest of the epic.**
Review findings by story: 7, 10, 8, 7, 16. Story 4.5 combined multiple complexity dimensions simultaneously: a new subsystem (`DiscoveryService`), cross-cutting adapter changes (`_RECONNECTING_REASONS` across all four adapters), async and transport-level error handling, and integration-style testing. The structural complexity (more moving parts) was visible during implementation. The behavioral complexity — particularly error-handling correctness across multiple layers — only became fully visible under review.

Three of the eight patches in Story 4.5 were in `probe_dsmr_endpoint` exception handling alone. The core logic was sound; the failure path topology was not pre-specified.

**Root cause:** When a story combines async I/O, transport errors, multi-layer exception propagation, a new subsystem, or cross-cutting adapter changes, implementation typically focuses on the happy path and explicitly-specified failure modes. Error paths that emerge from the *composition* of these dimensions are underestimated and underdocumented before implementation begins.

**Cross-cutting adapter changes show early scaling pressure.**
Story 4.5 required synchronized `_RECONNECTING_REASONS` updates across all four adapters. This was manageable at four adapters. The coordination overhead scales linearly as adapter count grows. The deferred finding in Story 4.5 explicitly called this out as a code smell. One qualifying cross-cutting change has occurred; the trigger is at one of two.

**Register maps remain operationally unvalidated.**
All five Modbus register map modules carry explicit `# PLACEHOLDER` headers. The adapters behave correctly — missing registers return `DegradedDeviceState`, physically invalid values are rejected by Pydantic. But the actual register addresses and scaling factors are illustrative. This creates two risk classes: (1) a `DegradedDeviceState` on every poll because the address is wrong — visible; (2) an `InverterState` with plausible values decoded from the wrong register — harder to detect, depends on what happens to be at that address. The test suite proves behavioral correctness against fake raw states; it does not prove that the raw states reflect what real devices report.

### Key Lessons

1. Structural closure gates work when they are mechanical, not manual. Zero open findings is a direct result of the pre-commit hook and hard closure rule, not of reviewer diligence alone.
2. Code review catches correctness bugs that implementation misses — especially in domain boundary enforcement (device ID rules, timestamp provenance, export visibility).
3. Behavioral complexity in error paths is harder to reason about during implementation than structural complexity. Pre-specifying error paths in dev notes reduces the review surface on complex stories.
4. Architecture boundaries that are enforced by type checking are more durable than boundaries enforced by convention. The `core/` vs `adapters/` constraint never bent because mypy makes violation a build error.
5. The system is architecturally and behaviorally correct but not yet operationally validated. Coverage proves the code does what we told it to do; it says nothing about whether we told it the right things.

### Critical Path — Before Story 5.1 Starts

**P1 — `DegradedDeviceState.reason` string contract**
The reason strings (`"reconnecting"`, `"dsmr_stale"`, `"ocpp_invalid_power"`, `"missing_register:40083"`, etc.) must be treated as a **cross-epic stable interface**, not a Story 5.1 implementation detail. Once StateStore interprets these strings to drive per-component state transitions and SSE exposes them to consumers, they are effectively public API.

Required before Story 5.1:
- Document the full set of current reason strings from Epic 4 adapters
- Specify naming rules: snake_case, additive-only evolution, parameterized pattern for `reason:detail` values
- Document semantic meaning of each reason string
- Reference table in Story 5.1 dev notes and architecture doc

**P2 — `SystemSnapshot` semantics**
Required before Story 5.1:
- Immutability model (frozen at construction — consistent with Epic 4 Pydantic patterns)
- Versioning: strictly monotonic integer, never reused
- Update model: **full snapshot replacement** — no partial mutation; readers always get a coherent snapshot with no locking required
- Device presence/absence handling: how absent devices are represented vs degraded devices
- Authoritative timestamp source per snapshot

### SSE Payload Shape Decision — Before Story 5.2

**P3 — Full snapshot vs delta**
Recommendation: full snapshots. Full snapshots are simple to implement, easy to test (assert complete payload against fixture), and produce consistent client behavior (any client joining mid-stream gets a complete coherent state on first message). Deltas require tracking state history and increase client complexity. Document decision in Epic 5 plan or architecture doc before Story 5.2 begins.

### P1 — DegradedDeviceState.reason Contract ✅ DEFINED

**Cross-epic stable interface. Additive-only evolution. Must be reflected in architecture doc and Story 5.1 dev notes.**

**Rules:**
- Format: `snake_case` string, non-empty, no whitespace
- Parameterized format allowed: `<reason>:<detail>` (e.g. `"missing_register:40083"`)
- Additive-only: existing values MUST NOT be renamed or removed once defined
- Consumers must treat unknown reason strings as generic degraded state (forward compatibility)
- New reason strings require explicit definition before use — not arbitrary free-form strings

**Current allowed reason strings (Epic 4 complete inventory):**

| Reason | Source | Meaning | Expected behavior |
|---|---|---|---|
| `reconnecting` | All 4 adapters | Underlying transport/protocol temporarily unavailable or reconnecting | Degraded, retained in snapshot |
| `dsmr_stale` | GridMeterAdapter | Latest DSMR reading exceeded 60s staleness threshold | Degraded grid meter state |
| `ocpp_invalid_power` | EVChargerAdapter | Invalid negative MeterValues power received | Degraded EV charger state |
| `missing_register:<addr>` | InverterAdapter, BatteryAdapter | Required Modbus register absent from raw state | Degraded device state |
| `invalid_register_value` | BatteryAdapter | Register present but value unsupported at domain level (e.g. BYD direction register outside {0,1}) | Degraded battery state |
| `device_id_mismatch` | InverterAdapter, BatteryAdapter | Raw state belongs to a different device_id than adapter expects | Degraded; raw data must not be trusted |
| `validation_error:<detail>` | InverterAdapter, BatteryAdapter, GridMeterAdapter | Decoded values failed Pydantic/domain validation | Degraded; data rejected |
| `missing_dsmr_field:<key>` | GridMeterAdapter | Required DSMR OBIS field absent from raw state | Degraded grid meter state |
| `ocpp_no_status` | EVChargerAdapter | Charger connection exists but no StatusNotification received yet | Degraded EV charger state |
| `ocpp_unknown_status:<status>` | EVChargerAdapter | OCPP status string not recognized by adapter mapping table | Degraded EV charger state |
| `unexpected_raw_state_type` | All adapters | Adapter received a raw state object of the wrong type | Degraded; do not attempt normalization |

**Not currently in codebase — reserved for future definition when a story introduces them:**
`device_not_responding`, `protocol_error`

### P2 — SystemSnapshot Semantics ✅ DEFINED

**Core properties:**
- **Immutable:** once created, must not be mutated
- **Versioned:** strictly monotonic integer, incremented on every update, never reused
- **Atomic replacement:** each update produces a completely new snapshot (copy-on-write); no partial mutation

**Structure:**
- Last-known state per configured device: `DeviceState | DegradedDeviceState`
- Snapshot-level metadata: `version` (monotonic int), `created_at` (UTC, generated at StateStore aggregation time)

**Behavior rules:**
- Updates replace the entire snapshot; readers always observe a fully consistent snapshot
- **Device absence — Option A chosen:** A configured/known device must remain represented in the snapshot even when degraded, unavailable, stale, reconnecting, or otherwise unusable. Temporary failure is represented as `DegradedDeviceState` with the appropriate reason string. Removing a device from the snapshot happens only when the device is explicitly removed from configuration or was never part of the configured system.
- Timestamp authority: adapter-provided timestamps represent measurement time; snapshot `created_at` represents aggregation time at the StateStore level

**Implications:**
- Consumers never infer device failure from a missing key — only from `DegradedDeviceState`
- No locking required for readers (copy-on-write model)
- Deterministic SSE and polling behavior
- Epic 7 degradation matrix evaluates a complete, consistent device set on every cycle

**Non-goals:** no in-place mutation, no partial updates, no reliance on adapter state after snapshot creation
