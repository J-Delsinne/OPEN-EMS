## Part 1: Epic Review

### What Went Well

**A1/A2 structural enforcement actually worked.**
The Epic 8 retro's biggest commitment was codifying mandatory orchestration artifacts (R1–R7) in `bmad-create-story` so they couldn't be skipped on high-risk stories. First fired on 9-0 (2026-05-10), and held across every A2-triggered story after.

- Story 9.4 hit **six A2 triggers simultaneously** — the most orchestration-heavy story in the epic — and R1–R7 all authored substantively. Implementation landed cleanly on the first dev pass.
- Story 9.5 demonstrated the gate works in the *other* direction: author evaluated T1–T7, none matched, the R1–R7 burden was correctly waived, and the story shipped lean.

This is direct evidence that the A1/A2 gate is not over-firing — false positives would have made the gate cost more than it saves; that didn't happen.

**The prep-story-before-consumer-story pattern scaled to four prep stories.**

| Prep | Closed deferred finding from |
|---|---|
| 9-0 | 8-2 `[policy_guard.py:97-100]` correlation_id mismatch; 8-5 capability-profile drift |
| 9-0b | 8-2 DB-backed active-constraints reload (P1 from Epic 8 retro) |
| 9-0c | 8-2 / 8-5 capability-profile failure semantics (P4 from Epic 8 retro) |
| 9-0d | 8-1 `[control_loop.py:54]` monthly peak stale-on-restart (P2 from Epic 8 retro) |

Four orchestration-runtime hazards graduated from "deferred" to "closed by full BMAD story" before any installer-facing code touched them. Story 9.3 cited 9-0b's contracts verbatim; 9.4 cited 9-0c's capability-failure paths and 9-0d's hydration ordering.

**Single-source-of-truth patterns held under installer workflow.**

- `ActiveConstraintsProvider` is the only path to `peak_limit_kw` / `battery_reserve_floor_percent` at runtime. `tests/unit/test_settings_seed_only.py` enforces this with a regex sentinel that catches `settings.X`, `_settings.X`, `self._settings.X` but not legal provider-snapshot reads.
- `device_registry` is the only table for installer-acknowledged devices — 9.2 extended with `role` and `role_assigned_at` columns rather than introducing a parallel role table.
- `deployment_validation_results` enforces a single-row invariant via `BEGIN IMMEDIATE; DELETE; INSERT;` inside one transaction.
- `WriteCapability` × `_SUPPORTED_MODELS` registry alignment validated at startup with fail-loud `SystemExit(1)` (9-0c's `validate_capability_registry_alignment()`).
- `_FIXED_ADAPTER_MODELS` cross-validated against capability registry at boot.

Five new tables, each with a clear ownership boundary. No duplicated state.

**The 9-0 cross-adapter command contract paid off downstream.**
`src/open_ems/adapters/__init__.py` now hosts the `COMMAND_CONTRACT_VERSION` constant + canonical contract docstring. All four adapter modules cite it. 9.4's `ProtocolAdapterFactory.probe` could be safely read-only because the contract clearly separates `send_command` (write path) from probe semantics. Without that clear separation, 9.4's "safe readiness check" guardrail would have been hard to enforce structurally.

**Test isolation pain caught early, fixed cheaply.**
9-0b discovered that `structlog.testing.capture_logs()` doesn't see events when the module logger was first bound during an earlier test (cache leakage from `cache_logger_on_first_use=True`). Fixed with a session-wide autouse `_reset_structlog_config` fixture in `tests/conftest.py`. Subsequent 9-0c / 9-0d / 9-1 / 9-2 / 9-3 / 9-4 / 9-5 all benefit without rediscovering the bug.

**Zero new dependencies across the epic.**
`uv.lock` did not change once. Five new tables + entire installer wizard + deployment validation + handoff guide — all on the existing stack. The cost of complexity went almost entirely into our own test suite, not into transitive dependencies.

**Process failure recorded:** review-checkbox state was not authoritative on Stories 9.3 and 9.4. The `bmad-code-review` workflow has no structural enforcement matching the `bmad-create-story` workflow's A1/A2 gate.

**The story-status / sprint-status / file-status triangle has no enforcement.**
Three pieces of state must agree for a story to be considered shipped:
1. The story file's `Status:` header
2. The entry in `sprint-status.yaml`'s `development_status:` map
3. The checkbox-state of review findings in the story file

The `bmad-code-review` workflow apparently reverts the `Status:` header to `in-progress` when patch findings remain as deferred sub-stories. But sprint-status is updated by a different workflow that doesn't see the revert. The two layers don't synchronize. We have AST-level enforcement on import boundaries and structural enforcement on R1–R7 orchestration artifacts. We have no enforcement on story-state consistency.

**Story 9-3 produced six named carry-over sub-stories.**
This is a re-emergence of the deferred-findings risk that Epic 8 specifically flagged. The named carry-overs are:

### Key Lessons

1. **Structural enforcement scales when the enforcement code is durable.** A1/A2 in `bmad-create-story` survived a six-A2-trigger story (9-4) without breaking. The pattern of "make the boundary structural, not procedural" works for story creation as well as it works for import boundaries.

2. **Review-closure discipline does NOT scale on procedural enforcement alone.** Epic 7 retro's A1 was insufficient at 8-4 complexity; Epic 8 retro's A3 was insufficient at 9-3 round-2 and 9-4 complexity. The same mechanical enforcement we gave to story creation must be applied to story closure.

3. **Status state is multi-source. Without a consistency check, divergence is inevitable.** Three writers (the dev workflow, the review workflow, the sprint-status workflow) update three different pieces of state that must agree. When workflow A reverts a status and workflow B doesn't see the revert, the system enters a state no human approved.

4. **Carry-over sub-stories need triage discipline, not just naming.** Round 2 of 9-3 named six `9-Y-*` items without bucketing them. The Epic 8 retro's classification rule (must-before / safe-during / acceptable-post) only protects against deferred-findings risk if it's applied *at the moment of deferral*, not retroactively at the next retro.

5. **Prep-story-before-consumer pattern stays effective at scale.** Four prep stories before five wizard stories produced cleaner late-epic stories than three prep before four wizard would have. Front-loading runtime-contract work continues to pay off; we should expect Epic 10 to need its own prep (R4 / `9-X` below).

### Significant Discovery — Epic 10 Story 10.2 Cannot Honestly Ship With `adapters={}`

Epic 10's Story 10.2 (EV override 4-state) requires that `Confirmed` state be entered only when `EVChargerState.session_active = true` is observed in the StateStore. For that observation to ever occur, the EV override POST must reach `PolicyGuard.authorize_and_dispatch()` → adapter → real OCPP command. With `adapters={}` at lifespan construction (Story 8-2 deferred-finding, explicitly preserved through 9-5), PolicyGuard rejects every command at P1 (`adapter_not_registered`). The 4-state lifecycle never advances past `Optimistic → Fallback`.

This was a known gap from 8-2 / 9-1 / 9-4 / 9-5. It is now blocking. Epic 10 as currently planned in `epics.md` implicitly assumes a working runtime adapter map.

**Resolution:** Insert `9-X-wire-adapter-map-into-policy-guard-and-control-loop` as a hard prep gate before Story 10.2 (preferably before Epic 10 planning begins).

`9-X` is A2-triggered (minimum: T1 lifecycle — adapter registration changes the adapter set PolicyGuard sees; T5 multi-adapter coordination — at least three adapter types simultaneously; T7 installer workflow orchestration — the wiring source-of-truth is `device_registry.role`).
