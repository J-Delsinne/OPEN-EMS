## Part 1: Epic Review

### What Went Well

**The architecture held under high orchestration complexity.**
Epic 8 was the first epic where multiple operational domains converged in a single story (8-4 alone fused watchdog lifecycle, retry/cancellation, systemd integration, fail-safe escalation, observability, and 4 prior-story deferrals). The architectural skeleton — import-boundary AST tests, `evaluate_cycle()` purity, `PolicyGuard.authorize_and_dispatch()` choke point, `peak_intervals` single-writer rule — was never violated. Every HIGH-severity bug found in review lived inside a single layer; none crossed boundaries. Boundaries enforced by code beat boundaries enforced by convention, again.

**The Epic 7 prep gates worked.**
8-0 (`ActionType` enum) and 8-0b (`PartialIntervalTracker`) shipped as full BMAD stories with 7 + 23 new tests respectively. 8-1's dev notes cite the tracker's contract verbatim. 8-2's dev notes cite `ActionType` members verbatim. The deferred string-dispatch and `current_interval_elapsed_seconds=900` boundary risks from Epic 7 never surfaced as live bugs in the consuming stories.

**Adversarial 3-layer review caught critical operational hazards.**
The 3-layer model in 8-5 used non-overlapping reviewer mandates (Blind Hunter → unsafe implementation patterns; Edge Case Hunter → lifecycle/runtime failures; Acceptance Auditor → spec drift). Coverage was orthogonal, not duplicative. Severity tagging on 8-4 surfaced 5 HIGH-severity bugs, two of which were operational hazards — `missed_count` arithmetic off by a factor of `threshold` (production audits would have undercounted by 2–3x), and cold-start `sd_notify` suppression (systemd would have killed the freshly-started process at first watchdog tick). Both were caught before merge.

**Story 8-3 set the cleanliness bar.**
13 unit + 3 command + 2 integration tests; followed Dev Notes pseudocode exactly; review produced 5 surgical patches and only 3 deferrals — and *zero* deferred items at story close (all classified or applied). Demonstrates that focused, single-domain stories with strong dev notes still ship at high quality.

**Best-ever follow-through on prior-retro commitments.**
All 9 commitments from Epic 7's retrospective (A1–A5, P1–P4) either landed in Epic 8 or are correctly carried forward. P1 and P2 became the prep stories. P3 was preserved in 8-2's IntentExecutor dispatch. P4 manifested in 8-2's `SimulatedBatteryAdapter` and 8-5's `tests/fixtures/scenarios.py`. A1 was visible in 8-1 and 8-2 dev notes.

### Challenges and Growth Areas

**Story 8-4 crossed from implementation into multi-domain orchestration — and the spec didn't carry the mandatory invariant analysis to match.**
The 5 HIGH-severity findings in 8-4 were not isolated coding mistakes. They were ownership / invariant problems caused by too many operational domains converging inside one story:

- `missed_count` arithmetic mixed up `threshold-window-seconds` with `per-cycle-interval-seconds`
- Cold-start `sd_notify` suppression because `last_cycle_completed_at_monotonic is None` was treated as "stalled" without a startup grace
- `_last_mode = new_mode` set before fail-safe-suppression check produced contradictory snapshot mode under exit-blocked recovery
- Entry audit cancellation could leave the state machine in entry-not-marked state (duplicate-entry risk)
- Tests #29 and #30 didn't actually verify the `retry_cancelled` warning log

A1 (orchestrator-gate guidance) from Epic 7's retro was visible in 8-1 and 8-2's dev notes but was *not* applied with sufficient force on 8-4. The story would have benefited from mandatory pre-implementation artifacts — state-transition table, impossible-state analysis (with cold-start coverage), cancellation ownership map, before-first-successful-cycle lifecycle review — landing in dev notes *before* `Status: ready-for-dev`. Soft guidance does not survive complexity climbs.

**Deferred-findings stock crossed the risk threshold.**
Epic 7 closed with ~15 deferred findings flagged as a risk threshold. Epic 8 added ~38 more. Most are correctly classified, but four cross directly into Epic 9 runtime semantics:

- DB-backed active-constraints reload (deferred 8-2)
- Restart hydration of monthly peak (deferred 8-1)
- Real adapter `send_command()` implementations (deferred 8-2 — currently `NotImplementedError` stubs)
- Capability-profile failure semantics (deferred 8-5 / 8-2)

Epic 9 is the first installer-facing persistent operational workflow epic. The acceptable runtime-risk level changes substantially.

**Cancellation audit schema asymmetry is a downstream-consumer trap.**
`_emit_cancellation_audit` lacks `detail.final_reason` while `_emit_failure_audit` includes it (deferred 8-5). Any downstream consumer that does `detail["final_reason"]` will `KeyError` on cancellation rows. Not a bug today; will be a bug once Epic 9 audit-log UI consumes these fields.

### Key Lessons

1. Orchestration-heavy stories require *mandatory* pre-implementation invariant analysis. Dev-notes guidance is insufficient once a story spans 3+ operational domains. The HIGH-severity findings in 8-4 are exactly what impossible-state analysis is designed to prevent.
2. Cross-cutting runtime primitives (`ActionType`, `PartialIntervalTracker`, real `send_command()` semantics) must be stabilized as full BMAD stories *before* orchestration stories consume them. The pattern that succeeded for 8-0 / 8-0b extends directly to Epic 9's pre-9.1 work.
3. Adversarial multi-layer review with non-overlapping reviewer mandates produces orthogonal coverage, not duplicated noise. The 3-layer model is the correct default for high-risk orchestration stories.
4. Severity tagging on review findings changes triage behavior. Without it, a 13-finding review reads as "lots of cleanup." With it, 5 HIGH findings read as "do not merge until resolved." The taxonomy works.
5. The architecture is durable. Epic 8 was the highest orchestration-complexity epic so far, and the architectural skeleton held. Continued investment in code-enforced (not convention-enforced) boundaries is justified.

### Cross-Epic Constraint to Carry Forward

**Single-Evaluator Principle still holds.** Epic 9's installer wizard collects configuration data and writes it to DB; it does **not** generate control intents. Every device command in Epic 9 (capability probing, deployment validation) must still flow through `PolicyGuard.authorize_and_dispatch()`. No bypass for "setup mode."

### Critical Path — Hard Gates Before Story 9.1

#### Story 9.0 — Real Adapter Command Execution Contracts and Implementations

A dedicated full BMAD story, modeled on the 8-0 / 8-0b prep pattern. Real `send_command()` behavior is no longer adapter-implementation-detail; it is foundational runtime infrastructure for the entire installer workflow. Distributing the implementation piecemeal across 9.x stories would recreate the orchestration coupling problem that Epic 8 exposed.

**Story 9.0 deliverables:**

- Per-adapter command contract docs (Battery, Inverter, EV Charger) covering: command surface, capability declaration, failure semantics, timeout/cancellation behavior, `correlation_id` round-trip, observed-state population
- Common failure semantics locked before implementation:
  - `CommandResult(status=failed)` vs `(status=timeout)` vs `(status=rejected)` — exhaustive guidance
  - Adapter exception → `CommandResult` wrapping (AR16) consistency
  - `applied=True` ⇔ `status=success` invariant maintenance (already enforced by Pydantic validator)
- Consistent retry/cancellation expectations across all controllable adapters
- Unified `correlation_id` propagation
- A single review surface for cross-adapter behavior — adversarial 3-layer review with severity tagging

**Sequencing:** Story 9.0 must complete (Status: done, all reviews resolved) before Story 9.1 ACs are written. Story 9.1's dev notes cite the 9.0 contracts verbatim.

**Owner:** Winston (per-adapter contract authoring) + Amelia (implementation)

#### P1 — DB-Backed Active-Constraints Reload (Full BMAD Story)

`PolicyGuard` currently reads `peak_limit_kw` and `battery_reserve_floor_percent` from `Settings`. Epic 9.3 writes these to a `constraints` table. PolicyGuard must reload from DB (with TTL or change-trigger pattern), not from process-startup `Settings`. Without this, constraint changes from the installer wizard would not take effect until process restart.

**Owner:** Winston (contract) + Amelia (impl)
**Gate:** Hard gate before Story 9.3 — strongly preferred before 9.1

#### P2 — Restart Hydration of Monthly Peak (Full BMAD Story, Small)

`ControlLoop._monthly_peak_kw` initializes to `0.0` and only updates on first interval rollover. Peak-limit decisions use stale data for up to 15 min after every restart. Installer workflow restarts the process; this becomes user-visible. Hydrate from DB during lifespan startup using an async-init pattern.

**Owner:** Amelia
**Gate:** Hard gate before Story 9.4 (deployment validation actually exercises peak-limit decisions)

#### P4 — Capability-Profile Failure Semantics (Doc + Targeted Tests)

Three paths must be unambiguous in PolicyGuard before Epic 9 wires real capability profiles:

1. `get_capability_profile()` returns a profile that *exists but lacks the requested write capability* (currently → reject with `capability_missing`)
2. The device is *unregistered* (currently → reject with `adapter_not_registered`)
3. The profile lookup itself *raises* (currently behavior under-tested)

Lock the contract; add targeted hardening tests; document in PolicyGuard module docstring.

**Owner:** Murat (test matrix) + Amelia (impl)
**Gate:** Before Story 9.2 (role assignment generates capability profiles dynamically)
