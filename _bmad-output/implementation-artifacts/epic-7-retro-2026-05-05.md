## Part 1: Epic Review

### What Went Well

**Architecture held under integration pressure.**
Epic 7 was fundamentally a composition problem — four independently-developed rule modules wiring into a single `evaluate_cycle()` orchestrator. The pure-engine import boundary (no `web`, `storage`, `adapters`, or `services` imports from any engine module) was never violated. AST import-boundary tests made violation physically impossible to ship without a failing test. The `EvaluationInput` extension pattern was applied consistently across all five stories with no regressions at any story boundary.

**`evaluate_cycle()` emerged as a clean, trustworthy interface.**
Epic 7 produced a single, deterministic entry point for the entire decision engine. Epic 8 can consume it without rework. The interface is stable, typed, and fully test-covered.

**Review functioned as a correctness tool throughout.**
31 review findings across five stories — all substantive correctness bugs, not style notes. The `battery_support_ev` guard missing `session_active` (Story 7.4) would have produced battery discharge with no load sink in production. `EvaluationResult(intents=(), decision_reasons=())` silently passing all validators (Story 7.5) was a model invariant violation. Review caught both before they reached the codebase.

**A1 process gate paid dividends in Story 7.5.**
Story 7.5 used structured "Critical Implementation Decision" blocks with explicit source-of-truth checks and warnings to grep actual source before writing string mappings. This directly prevented EV reason-code drift from producing broken decision reason strings in the final `EvaluationResult`.

**All Epic 4 retro action items followed through.**
First time three-for-three follow-through has been achieved.

### Challenges and Growth Areas

**Story 7.5 had the heaviest review load of the epic (10 findings, 6 patches).**
Orchestrator stories that compose multiple independent modules accumulate the assumptions each module made independently. The review surface scales with the number of compositions. This is structural, not a failure of any specific story.

**Reason-code drift: untyped strings as cross-module interface.**
Story 7.5 dev notes anticipated `ev_charge_outside_window_no_session` as an EV reason code. The actual code produced `ev_charging_window_inactive`. The drift was caught because the dev notes explicitly instructed the agent to grep the source. Without that instruction, the mismatch would have produced incorrect human-readable decision reasons in the event log. This is the upstream symptom of a broader deferred issue: action_type and reason_code strings are unregistered, untyped, and undiscoverable without source inspection.

**Deferred findings accumulation has crossed a risk threshold.**
15+ deferred findings are now carried across the engine layer. Individually each is justifiable. Collectively they represent a surface area that becomes execution risk in Epic 8, where intents drive real device commands. The deferred action_type string issue (flagged in 7.3, 7.4, and 7.5) was explicitly classified against Jordan's triage threshold and found to cross it.

**Story 7.5 story file status not updated after code review.**
The story file reads `Status: review`; sprint-status reads `done`; all review patches are confirmed applied. Documentation gap that will confuse Epic 8 developers picking up context. Action A3 covers cleanup.

### Key Lessons

1. Architecture boundaries enforced mechanically (AST tests + import rules) are more durable than boundaries enforced by convention. Five stories, zero violations.
2. Orchestrator and integration stories need stronger pre-implementation structure than isolated rule stories: composition-risk analysis, impossible-state tables, source-of-truth ownership per datum. Strengthened A1 carries this forward.
3. Deferred findings must be triaged against a runtime-risk threshold before epic transitions. The rule: *if a deferred issue can produce an invalid intent, misleading reason, unsafe dispatch, or ambiguous watchdog behavior, it becomes a prerequisite fix or an explicit Epic 8 acceptance criterion — not background noise.*
4. String-based dispatch is a first-class risk once action types cross into runtime execution. An `ActionType` enum with exhaustive dispatch is required before Epic 8's IntentExecutor is built.
5. A1 process gate works when it is applied proactively, not reactively. Story 7.5 applied it correctly; the outcome was better-structured dev notes and a prevented bug.

## Part 2: Epic 8 Preparation

### Epic 8 Preview — Control Execution and Safety Enforcement

| Story | Focus |
|---|---|
| 8.1 | Runtime control loop: adapter polling, StateStore publishing, EvaluationInput assembly, PeakContext construction |
| 8.2 | IntentExecutor, PolicyGuard, command dispatch |
| 8.3 | Retry policy, timeout handling, idempotency enforcement |
| 8.4 | Watchdog, fail-safe transition, recovery |
| 8.5 | End-to-end decision engine simulation |

**Dependencies on Epic 7:**

- `evaluate_cycle(EvaluationInput) → EvaluationResult` — the single entry point the control loop calls every tick
- `BatteryIntent`, `EVChargerIntent` — what IntentExecutor translates to device commands
- `PolicyGuard.authorize_and_dispatch()` — referenced throughout Epic 7 as the mandatory safety gate; Epic 8 implements it
- `PartialIntervalTracker` — consumed by Story 8.1 to construct `PeakContext`; does not yet exist

### Single-Evaluator Principle (New Cross-Story Constraint for Epic 8)

`evaluate_cycle()` is the **sole generator of control intents** in the system. Every other component in Epic 8 either:
- **Provides input** to the evaluator (control loop assembles `EvaluationInput`)
- **Enforces safety** on the output (PolicyGuard validates and dispatches intents)

No component may generate competing control decisions. Every dispatched command must be traceable to an `EvaluationResult` intent. This constraint must appear in Epic 8's cross-story constraints section alongside the existing "no adapter calls, no database writes" engine constraints.

### Critical Path — Before Story 8.1 Starts

**P1 — PartialIntervalTracker contract (full BMAD story)**
Define the tracker's public interface, update semantics, rollover behavior, and ownership in the runtime loop. Implement with complete quality gates (pre-gate, red/green, review).

Key invariant: *`PeakContext` must only be built from an active interval. If the interval is complete, the tracker finalizes and rolls over first. Only then does the control loop call `evaluate_cycle()`.* This resolves the long-deferred `current_interval_elapsed_seconds=900` boundary question.

Once complete: update Story 8.1 ACs to include the finalize-before-evaluate invariant as an explicit acceptance criterion.

**P2 — ActionType enum (full BMAD story)**
Replace all `action_type` string literals across `battery_control.py`, `ev_scheduling.py`, `evaluator.py`, and `energy_balancing.py` with an exhaustive `ActionType` enum. Dispatch logic must be exhaustive over enum members — unknown member raises immediately, does not produce silent `hold`. Revisit `EnergyStrategy` dispatch to raise on unknown strategy rather than fall back gracefully. Deliverable includes exhaustive-dispatch unit tests.

Once complete: update Story 8.2 ACs to require `ActionType` enum dispatch in IntentExecutor.

**Sequencing:** P1 and P2 complete → update Epic 8 story ACs directly from those definitions → proceed to Story 8.1.

### Before Story 8.2 Starts

**P3 — Document `reduce_ev_charge_rate` fall-through in Story 8.2 context**
Current behavior: peak-limit candidate with `action_type="reduce_ev_charge_rate"` (safety band) reaches `ev_scheduling.py` but falls through to `hold` because `_CHARGE_ACTIONS` does not include it. This is intentional — `ev_scheduling.py`'s internal peak-projection guard already handles EV charge suppression under overshoot. This invariant must be visible in Story 8.2's dev notes before IntentExecutor is implemented, or the developer will treat the fall-through as a bug.
Owner: Paige

### Parallel Preparation

**P4 — Integration test infrastructure scope for Story 8.2**
Story 8.2 requires an end-to-end integration test: typed intent → IntentExecutor → candidate command → PolicyGuard → simulated adapter → CommandResult → audit event. Scoping the simulated adapter, audit event verification approach, and required fixtures before Story 8.2 starts prevents mid-story discovery delay.
Owner: Murat
