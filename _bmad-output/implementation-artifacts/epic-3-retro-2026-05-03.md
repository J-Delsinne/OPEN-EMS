## Part 1: Epic Review

### What Went Well

**Contract-first design proved its value immediately.**
Story 3.1 didn't just define an interface — it locked architectural boundaries before any implementation began. All three subsequent adapters implemented cleanly against `ProtocolAdapter` with no retrofit, no boundary drift, and no surprises. Epic 4's normalization layer starts from a stable, type-checked foundation.

**Fake transport fixtures were the correct pattern for protocol work.**
`_FakeAsyncModbusClient`, `_FakeWebSocket`, and `FakeTransport` allowed every failure mode — timeouts, disconnects, malformed payloads, reconnect flows — to be exercised deterministically without real hardware. This directly delivered the Epic 2 retro B2 commitment and sets the standard for all future adapter work.

**Raw/domain boundary discipline held across all four stories.**
No energy semantics (`soc_percent`, `grid_power_kw`, `session_active`) leaked into the adapter layer. The explicit AC5 in Story 3.1 and the raw state boundary notes in each subsequent story enforced this mechanically. Epic 4's normalization layer has unambiguous ownership of everything above `RawProtocolState`.

**Test suite growth was qualitatively meaningful.**
The increase from 186 → 284 tests reflects coverage of async lifecycle, reconnection flows, one-shot logging, and error propagation — not just happy paths. 86.70% coverage at close provides genuine confidence.

**Multi-model workflow remained architecturally stable.**
Codex handled Stories 3.1 and 3.2; Claude Sonnet 4.6 handled 3.3 and 3.4. No architectural drift, no boundary inconsistency. The constraints, typed Protocols, `extra="forbid"` models, and review process were strong enough to produce consistent output regardless of model. This validates the approach for long-running AI-assisted projects.

**CI discipline held without blocking progress.**
Strict `mypy --strict`, `ruff`, and `pytest` with coverage gate were maintained through all four stories without blocking iteration.

Winston (Architect): "Epic 3 is where the import boundary and Protocol typing paid off. No drift, no retrofitting. That's what boring architecture should do."

Murat (Test Architect): "The fake transport pattern is now the established pattern for any Epic that touches protocol communication. It scales."

### Challenges and Growth Areas

**Story 3.3 (OCPP) closed with two unresolved review findings.**

The OCPP adapter is architecturally distinct from Modbus and DSMR: it is push-based (charger initiates the WebSocket connection), event-driven, and has more complex state transitions. This elevated the review surface. However, two findings were not resolved before the story was marked done:

- 🔴 **[High]** `except Exception: pass` in the message loop — directly violates the fail-fast anti-pattern rule written into the story's dev notes before implementation began
- 🟡 **[Med]** `last_call_error` not cleared after a successful subsequent command — produces misleading state for consumers

The high finding in particular should not have survived review. Its presence indicates the review standard was not consistently applied under complexity. The story was marked done in a state that is not production-safe.

**Story 3.3 had a thinner implementation record than other stories.**
No pre-story gate log entries, no red-phase evidence in the debug log. The completion notes are present but lighter than Stories 3.1, 3.2, and 3.4. This correlates with the review gaps.

**`tzdata` dependency was a runtime surprise.**
`ZoneInfoNotFoundError` from `dsmr_parser` appeared at module-import time on Windows/Python 3.14. Caught and fixed in Story 3.4, but it was not anticipated during planning. For future stories consuming third-party parsers, platform compatibility should be checked earlier.

**Review finding volume was high across the epic.**
25 review items across 4 stories (3.1: 6, 3.2: 10, 3.3: 4, 3.4: 5). The majority were patched cleanly. But the volume — especially Story 3.2's 10 items — suggests the review process is catching things that could have been prevented earlier by mechanical enforcement.

**B5 Root Cause:**
A4 (event-name cleanup) was partially addressed implicitly but never explicitly verified. A5 (pin uv image), A6/A7 (pre-commit hooks/checklist) were not implemented. The absence of A6/A7 is now a **confirmed contributing cause** of the Story 3.3 closure failure — no automated enforcement meant manual review discipline was the only gate, and it degraded under OCPP complexity.

The structural gap: retro action items had no mechanism to re-surface at the start of the next epic. They were carried by memory, and memory failed.

### Key Lessons

1. Contract-first design scales to multi-story epics with no architectural drift, as long as the contract is typed and enforced.
2. Fake transport fixtures are the correct and sufficient pattern for protocol adapter testing. No real hardware required, no happy-path-only coverage.
3. A story must not be marked done with open `[ ]` review findings. "Functionally complete" is not the same as "done."
4. Complexity is a review risk signal that should trigger more scrutiny, not less. The OCPP adapter was harder — that meant the review needed to be more careful, not equivalently careful.
5. Retro action items must be structurally re-surfaced at the start of the next epic. Memory is not a tracking mechanism.
6. Process commitments that were not delivered (A5, A6/A7) do not fade — they accumulate risk and eventually manifest as real failures.

## Part 2: Epic 4 Preparation

### Epic 4 Preview — Device Abstraction Layer

Epic 4 normalizes raw protocol data into typed domain `DeviceState` models, exposes validated capability profiles, and handles device discovery and automatic reconnection. It directly wraps Epic 3's adapters.

| Story | Focus | OCPP dependency |
|---|---|---|
| 4.1 | `DeviceState` model, `DeviceAdapter` protocol, energy sign conventions | None — defines the layer above adapters |
| 4.2 | Modbus device normalization with register maps | None — Modbus adapter is clean |
| 4.3 | OCPP and DSMR device normalization | **Blocked** until OCPP adapter is production-safe |
| 4.4 | Device capability profile system and capability gate | None at story start |
| 4.5 | Device discovery and connection management | Indirect |

### Sequencing Decision

**Controlled parallelism:**
- Story 4.1 starts immediately — it is foundational and has no dependency on adapter correctness
- OCPP fix (C1 + C2) executes as an immediate priority patch in parallel
- Story 4.3 is **strictly blocked** until the OCPP adapter is production-safe

Rationale: building normalization logic on top of an adapter that swallows exceptions would hide real errors, produce misleading device state, and create debugging ambiguity in the domain layer. The risk of that architecture debt is not acceptable.

### Story 4.3 Hard Entry Gate

Before Story 4.3 may start:
- ✔ C1 resolved: no `except Exception: pass` in Story 3.3 OCPP adapter
- ✔ C2 resolved: `last_call_error` cleared after successful subsequent command; test coverage confirmed
- ✔ Zero open `[ ]` findings in the Story 3.3 file

### Epic 4 General Story Closure Gate

Before any Epic 4 story may be marked done:
- ✔ Zero open `[ ]` review findings in the story file
- ✔ C3 resolved: uv image pinned in CI
- ✔ C4 resolved: pre-commit hooks active
- ✔ C7 resolved: `BLE001` (blind exception) ruff rule confirmed active and not suppressed
